# Go v2 API surface: capability coverage and sign-off

This is the sign-off artifact for [#27306](https://github.com/Azure/azure-sdk-for-go/issues/27306),
*Go v2: API surface review & v2 API design*.

The v2 public API is defined by the Go source in this module, not by this document: `go doc` and
APIView render it directly, and prose restating signatures goes stale the moment code lands. Read
the surface with

```
go doc -all github.com/Azure/azure-sdk-for-go/sdk/data/azcosmos/v2
```

rather than from a checked-in copy, for the same reason. What this document records is the part the
code cannot state for itself — how far the surface covers the planned capability set, what the
driver's C ABI can and cannot express today, and the decisions the crew is being asked to sign off
on.

## Capability coverage

**Coded** — present in the v2 Go surface. **Expressible** — the C ABI supports it, so it is a
matter of writing the binding. **ABI gap** — the Go API cannot be built until the native crate
exposes it, regardless of what the Go SDK does.

## Decisions being signed off

Each of these departs from v1, from an Azure SDK for Go norm, or from both. They are stated here so
the sign-off is on the record rather than distributed across PR threads.

1. **`Error` is not `*azcore.ResponseError`.** There is no `*http.Response` to put in one. `Error`
   carries the fields the C ABI exposes, and callers branch on `Code` — the shape `azservicebus`
   uses, which faces the same problem of being a non-HTTP data plane.
2. **`ClientOptions` does not embed `azcore.ClientOptions`.** `Transport`, `Retry` and the policy
   hooks have nowhere to be applied when the driver executes the operation. Advertising them and
   ignoring them is a worse failure mode than not offering them.
3. **`Code` is a curated classification, not the driver's error enum.** Most of the ABI's ~30 codes
   describe faults inside the binding. `Code` is computed from status *and* sub-status, because
   Cosmos overloads 404 and 410 with sub-status 1002 and a status-only mapping would tell callers
   something categorically wrong.
4. **`Close` returns an error and drains in-flight operations.** Driver handles are explicitly
   freed, so an operation still running at teardown is a use-after-free in Rust-owned memory rather
   than a nil panic.
5. **The driver runtime is not exposed.** The ABI's runtime handle is shareable and the Rust SDK
   surfaces it. Adding sharing later is not a breaking change; removing a type we regret is.
6. **Read and write options are split.** Consistent with decision 2: a read has no content-response
   setting and a create has no consistency strategy.
7. **Reads take a `ReadConsistencyStrategy`, not a consistency level.** The driver's strategy enum
   is `Default | Eventual | Session | LatestCommitted | GlobalStrong` — it has no
   `BoundedStaleness` or `ConsistentPrefix`, so the account enum would have been unbindable. The Go
   type omits `LatestCommitted`, because the C ABI's mirror of the enum has no value for it (see
   open item 7), and adds a zero value meaning "use the account's level", which the ABI spells
   `UNSET`.
8. **Item payloads are `[]byte`.** The ABI moves opaque bytes. Typed helpers can be layered on later
   without a breaking change.
9. **v1's query engine, effective-partition-key hashing and routing caches are not carried over.**
   The driver owns them; reimplementing them in Go is what v2 exists to stop doing.
10. **cgo is required, and WebAssembly support is dropped.** v1's wasm transport cannot bind to a
    native driver.

## Open items blocking sign-off

1. **Pin the native driver version.** `nativeDriverVersion` is provisionally `0.1.0`. Needs the Rust
   crew to name the build Go v2 GA will ride on, and a statement of the ABI compatibility guarantee
   within a pin.
2. **Change feed has no operation kind in the C ABI.** The driver crate implements change feed
   (`ChangeFeedStartFrom` in `models/cosmos_operation.rs`), so this is a native-layer gap rather
   than a driver gap — but the Go change feed API cannot be built until it is exposed. Note that
   the header's own comments on `cosmos_submit_operation` name change feed as a feed kind routed
   through submit, so the intent may be that it arrives without a distinct operation kind; that
   needs confirming. It is in the planned capability set, so it needs an owner and a date.
3. **Throughput control groups can be named per operation but not registered.** The Rust SDK
   registers them on the client builder; the C ABI has no equivalent, so the field is currently
   unusable end to end.
4. **Entra ID cannot cross the ABI.** Only master-key account references exist. Tracked by
   [#27304](https://github.com/Azure/azure-sdk-for-go/issues/27304); the `NewClient` signature in
   this surface is a proposal until that lands.
5. **Diagnostics have no representation.** The completion's diagnostics handle is reserved and
   always NULL. Tracked by [#27305](https://github.com/Azure/azure-sdk-for-go/issues/27305). v1
   exposed `Diagnostics` on every response and `DiagnosticsFromError`, so this is a visible
   regression for v1 users until it is designed.
6. **PPAF and hedging have no ABI surface.** Both are in the planned capability set.
7. **`LatestCommitted` read consistency is unbindable.** The driver's
   `ReadConsistencyStrategy` has a `LatestCommitted` variant, but the C ABI's mirror of that enum
   has no corresponding value, so it is omitted from the Go type. Adding it later is not a breaking
   change; confirm whether it is meant to be reachable at all.
